# D-BRAN

[![Status](https://img.shields.io/badge/status-research%20prototype-orange)](#project-status)
[![Framework](https://img.shields.io/badge/framework-PyTorch-ee4c2c)](https://pytorch.org/)
[![Task](https://img.shields.io/badge/task-sparse--IMU%20pose%20estimation-blue)](#overview)

**D-BRAN** is a distributed bidirectional recurrent architecture for full-body human pose estimation from six sparse inertial measurement units (IMUs).

The pose pipeline is divided into five anatomical branches that share the root IMU as a common reference. The current checkpoint set contains the final Pose-S1, Pose-S2, Pose-S3, and learned rotation-fusion models, together with the original TransPose translation branches.

Beyond the original AMASS/DIP-IMU/TotalCapture training data, the repository also includes a full pipeline for capturing custom Xsens + OptiTrack sessions and fine-tuning every stage on them — see [Fine-tuning on custom captures](#fine-tuning-on-custom-captures-optitrack--xsens).

> This repository represents the validated research implementation, with a working Xsens live-capture path and an Xsens–Unity real-time demo. Installation requirements and full reproducibility documentation will continue to be consolidated.

---

## Overview

D-BRAN estimates full-body pose using six IMUs placed on:

- left forearm;
- right forearm;
- left lower leg;
- right lower leg;
- head;
- root/pelvis.

The architecture preserves the staged pose-estimation strategy while distributing the computation across anatomical branches.

```text
Six sparse IMUs
      │
      ├── shared root reference
      │
      ├── left-leg branch
      ├── right-leg branch
      ├── trunk-head branch
      ├── left-arm branch
      └── right-arm branch
      │
      ▼
Pose-S1: distributed leaf-joint position estimation
      │
      ▼
Pose-S2: distributed full-joint position estimation
      │
      ▼
Pose-S3: distributed reduced-joint rotation estimation
      │
      ▼
Learned residual rotation fusion
      │
      ▼
Full SMPL pose
```

The original TransPose `Trans-B1` and `Trans-B2` modules are retained for translation estimation.

---

## Final architecture

| Stage | Organization | Hidden size | Output |
|---|---:|---:|---|
| Pose-S1 | 5 distributed branches | 32 | Leaf-joint positions |
| Pose-S2 | 5 distributed branches | 16 | Full-joint positions by anatomical branch |
| Pose-S3 | 5 distributed branches | 16 | Reduced-joint 6D rotations by anatomical branch |
| Rotation fusion | Learned residual fusion | 16 | Refined 90-dimensional rotation representation |
| Translation | Original Trans-B1 and Trans-B2 | Original configuration | Root translation |

Pose-S1 uses one local IMU and the shared root IMU for each branch. Pose-S2 and Pose-S3 continue the distributed processing with branch-specific joint subsets. The fusion network refines the assembled Pose-S3 output before conversion to the full SMPL pose.

### Parameter count

The current full-pipeline profiler reports:

| Pipeline | Parameters | FP32 parameter size |
|---|---:|---:|
| Original TransPose full pipeline | 4,798,771 | 18.306 MB |
| D-BRAN pose pipeline + original Trans-B1/B2 | 1,603,357 | 6.116 MB |

The resulting parameter ratio is **0.3341**, corresponding to approximately **66.6% fewer parameters** than the original full pipeline.

## Fine-tuning on custom captures (OptiTrack + Xsens)

Every stage can be fine-tuned on a custom motion-capture session instead of (or in addition to) AMASS/DIP-IMU/TotalCapture. This is the workflow used to specialize the pipeline to a specific subject or setup, using an OptiTrack volume as ground truth and Xsens MTw sensors as the sparse-IMU input.

### 1. Capture

```text
scripts/xsens/xsensDataCapture.py
```

Runs the two-step static calibration (global reference alignment, then a six-sensor T-pose — same procedure as `scripts/xsens/calibrate_xsens.py`) and then captures calibrated Xsens data, bounded by `--max_seconds` (wall-clock, from real frame timestamps) rather than raw frame count, so the take stops at the same real-world instant as a fixed-duration Motive Take. It has **no dependency on `DBranPipeline`, CUDA, or any neural network** — only UDP receive + calibration — so it sustains a true, consistent 60 Hz instead of the ~50 Hz effective throughput seen when running full online inference during capture (see [Native Xsens bridge](native/xsens_bridge/README.md) for why).

Dropped or incomplete synchronized frames are saved as `NaN` placeholders (`is_missing` field) rather than guessed at capture time — see the next section.

Record the corresponding Motive Take at the same time, with a sharp, marked gesture performed at both the start and the end (within the first/last ~10 seconds) while both systems are already recording. The two recordings do not share a clock; this gesture is what the alignment step uses to sync them.

### 2. Fill dropped Xsens frames

```text
scripts/data/fill_missing_xsens_frames.py
```

Fills the `NaN` gaps left by the capture step using the valid frames immediately before and after each gap: linear interpolation for acceleration, geodesic (axis-angle) interpolation for orientation. Run once per capture file before using it further.

### 3. Motive export

Export each Take as CSV with: **Units = Meters**, **Use World Coordinates = OFF** (so bone rotations are already local/parent-relative, matching SMPL), **Exclude Fingers = ON**, **Rotation Type = Quaternion**, **Skeleton and Markerset Bones = ON**. Axis Convention "Entertainment" (X=left, Y=up, Z=forward) already matches the Xsens calibration frame — leave it as-is.

### 4. Motive CSV → SMPL pose ground truth

```text
scripts/data/extract_optitrack_pose_gt.py
```

Converts each Take CSV into SMPL axis-angle pose + root translation. Canonicalizes quaternion sign before conversion (avoids a near-identity rotation reading back as ~360°), re-expresses joints 1–23 relative to their own rotation at a reference frame early in the take (removes a constant offset between Motive's rest pose and SMPL's zero pose — the root joint is left in the global frame), and linearly interpolates any fully/partially blank rows from a momentary Motive tracking-solve failure.

### 5. Align Xsens with the Motive ground truth

```text
scripts/data/align_and_package_dataset.py
```

Neither recording shares a clock, so this detects the marked start/end gesture in a movement-energy signal from each stream (frame-to-frame pose delta for Motive, acceleration norm for Xsens), fits a linear frame-index mapping from the two anchor pairs, and resamples the Motive pose/translation onto the Xsens timeline. Produces the standard `{'acc','ori','pose','tran'}` dataset. Takes with no closing gesture (recording cut off early) can be aligned with `--no_end_gesture_takes` using only the start anchor.

### 6. Finalize into per-sequence files

```text
scripts/data/finalize_dbran_optitrack_dataset.py
```

Converts the aligned dataset into individual per-sequence files matching the schema used everywhere else in the repo (`acc, ori, pose, tran, joints, shape, source, index`), computing `joints` via SMPL forward kinematics with the mean body shape (no subject-specific shape fit is done — this only affects bone *lengths* used for position targets, not the pose/rotation ground truth).

### 7. Fine-tune each stage

Every training script accepts a flag to continue from an existing checkpoint instead of training from scratch:

| Stage | Script | Flag | Notes |
|---|---|---|---|
| Pose-S1 | `train_pose_s1_distributed.py` | `--pretrained_checkpoint <file>` | One branch per run (`--target`); pass **each branch's own checkpoint file** |
| Pose-S2 | `train_pose_s2_full_distributed.py` | `--pretrained_checkpoint_dir <root>` | Supports `--target all`; per-target path is built automatically |
| Pose-S3 region | `train_pose_s3_region.py` | `--pretrained_checkpoint_dir <root>` | Supports `--target all`; per-target path is built automatically |
| Pose-S3 fusion | `train_pose_s3_rotation_fusion.py` | `--pretrained_checkpoint <file>` | Single unified model, not per-branch |

Architecture hyperparameters (`proj_dim`, `rnn_hidden`, `rnn_layers`, `dropout`) are read from the checkpoint automatically, so a mismatched `--proj_dim`/etc. on the command line can't silently break weight loading.

**Pose-S1 uses a single file path** (`--pretrained_checkpoint`) because each of the 5 branches is architecturally identical (same input/output shape), so pointing every branch at the same file *loads without error but is semantically wrong* — each branch must start from its own weights. Pose-S2/S3 use `--pretrained_checkpoint_dir` instead specifically to make that mistake impossible: the per-target filename is built automatically.

Pose-S2 and Pose-S3 need the *previous* stage's predictions as part of their input, so fine-tuning them requires precomputing those predictions from your already-fine-tuned upstream checkpoints first — otherwise the new stage would train on inputs that don't match what the fine-tuned upstream stage actually produces:

```text
precompute_pose_s1_predictions.py       --distributed_root_dir checkpoints/retrained/pose_s1_5branch_32h
precompute_pose_s2_full_distributed_outputs.py  --weights_root checkpoints/retrained/pose_s2_full_distributed
precompute_pose_s3_region_outputs.py    --weights_root checkpoints/retrained/pose_s3_5branch_16h
```

New checkpoints are saved under `checkpoints/retrained/`, never overwriting the validated originals.

### What to expect

Evaluated per stage against the original checkpoint on the standard TEST benchmark, fine-tuning trades general accuracy for accuracy on the custom capture (validation error on the custom data typically lands at or below the original model's TEST error, confirming genuine learning rather than noise):

| Stage | TEST degradation (single-stage) |
|---|---|
| Pose-S1 | +43% to +116% |
| Pose-S2 | +14% to +27% |
| Pose-S3 (region) | +9% to +37% |
| Pose-S3 (fusion) | +3% |

Degradation shrinks at each later stage — each one receives an already-processed input from the stage before it, so it has less to learn from scratch and less room to overfit.

**This does not hold when all four fine-tuned stages are chained together end-to-end** (via `scripts/profile/profile_full_pipeline_fivebranch.py` pointed at all four `checkpoints/retrained/...` paths at once): small per-stage degradations compound, since each fine-tuned stage now actually receives its immediate upstream stage's *fine-tuned* (and therefore also slightly degraded, on general data) output, not the original upstream predictions used in the isolated per-stage comparisons above. The full chained pipeline shows noticeably worse TEST-benchmark accuracy than any single stage's isolated number would suggest. Full end-to-end fine-tuned performance should always be checked with the profiler rather than inferred from the per-stage table.

## Evaluation and profiling

### Smoke test

The following command loads every checkpoint and evaluates one sequence:

```bash
python scripts/profile/profile_full_pipeline_fivebranch.py \
  --raw_list_file data/dataset_train/test.txt \
  --max_sequences 1 \
  --profile_repeat 1
```

This verifies:

- original TransPose checkpoint loading;
- all five Pose-S1 branches;
- all five Pose-S2 branches;
- all five Pose-S3 branches;
- learned rotation fusion;
- original Trans-B1 and Trans-B2;
- offline pose evaluation;
- throughput and CUDA-memory profiling.

### Full offline evaluation

```bash
python scripts/profile/profile_full_pipeline_fivebranch.py \
  --raw_list_file data/dataset_train/test.txt \
  --profile_repeat 1
```

### Online protocol

```bash
python scripts/profile/profile_full_pipeline_fivebranch.py \
  --raw_list_file data/dataset_train/test.txt \
  --evaluate_online \
  --profile_repeat 1
```

The profiler reports:

- SIP error;
- angular error;
- positional error;
- mesh error;
- jitter;
- parameter count;
- time per frame;
- throughput;
- peak CUDA memory.

The optional robustness hook is not part of the final pipeline. A message indicating that `robustness_full_pipeline_hook` is unavailable can be ignored during standard evaluation.

## Planned work

- Reduce per-frame inference cost of the live pipeline (`run_dbran_live.py`) to close the gap between the ~50 Hz effective throughput observed and the 60 Hz target — candidates: `--cuda_streams` (parallelize the 5 anatomical branches instead of running them sequentially) and `torch.backends.cudnn.benchmark = True` (added, not yet benchmarked against real sustained-session throughput).
- Investigate reducing the cascading accuracy loss seen when chaining all four fine-tuned stages together (see [What to expect](#what-to-expect)) — e.g. more conservative Pose-S1 fine-tuning specifically, since its degradation is the largest and propagates through every later stage.
